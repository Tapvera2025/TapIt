# Step 9 — Payroll (P2)

> **For agentic workers:** Implement task by task and review each task before continuing. The repository's actual interfaces and migrations take precedence over sketches in the design spec. A green unit suite is not the PostgreSQL or payroll reconciliation gate.

**Goal:** Deliver §14 and PRD P2: accepted dated payroll configuration, salary history, a complete frozen monthly snapshot, deterministic payslip calculation, review and publication, immutable revisions, and employee access. A complete cycle must reconcile with the underlying attendance days for every included person.

**Starting point (28 September):** Step 8 is implemented. Migration `0063_break_management.sql` already owns `payroll_input`; `modules/payroll/input.ts` writes break deductions and `modules/payroll/facade.ts` registers that writer. `BreakFacade.unresolvedBreaches` already returns the precise publish blockers. There are no salary, run, payslip, config or ledger-intent tables. `AttendanceFacade` does not yet offer `snapshotPeriod` or `openItems`, and attendance recalculation does not yet emit `attendance.day-changed`. The tenant DAL currently opens `READ COMMITTED` transactions only, so the frozen read needs a small DAL isolation option. The break evaluator writes its watermark from `calculation_version`, but its stale scan/index compare with `calculated_input_version`; resolve this mismatch before payroll uses the watermark. Use migration `0064_payroll.sql`; do not recreate or edit migration 0063.

**Architecture:** Payroll owns payroll tables and the pure money calculation. Attendance owns attendance rows and serves period snapshots and open items through its facade; break-management serves unresolved breaches through its existing facade. Employee and organization facts come through their facades or explicitly defined read ports. A run stores the *whole* input set per employee; compute workers use only that frozen JSON. A later live read inside the publish transaction checks every frozen input before publication. A narrow accounting-owned `LedgerFacade.post` stores a balanced posting intent in that same transaction until full accounting arrives. Published slips and lines are database-immutable; changes create linked revisions.

## Decisions and gates to pin before writing migration 0064

- **Configuration starts empty (D15).** HR and the CA provide rates, eligibility, wage bases, rounding and any night/overtime policy; a named authorized person accepts each dated version. No previous-system rate or assumed statutory value is seeded. A run without a complete accepted config fails with named missing fields. Overtime and lateness do not become pay lines without an accepted explicit rule (Q5/Q10); the one night-allowance method, if enabled, comes from the accepted config (Q13).
- The acceptor records the effective-dated primary source and CA/HR approval for each statutory choice. Evidence stores issuer, title, source/publication date, effective date, URI or official reference, and a checksum plus immutable object reference when a copy is retained. Check current issuer material at acceptance, such as [EPFO employer notifications](https://www.epfindia.gov.in/site_en/For_Employers.php/Disablitity.php), [ESIC publications](https://www.esic.gov.in/Publications/ESIAct1948Amendedupto010610.htm) and the [Ministry's Code on Wages text](https://labour.gov.in/sites/default/files/the_code_on_wages_2019_no._29_of_2019.pdf); this plan supplies no statutory values.
- **Money:** Pure calculation uses integer paise for totals and exact decimal/rational intermediate values. Round half-up to a whole rupee once for each displayed earning/deduction line, then sum displayed lines; no binary-float money. Existing `payroll_input.amount numeric(14,4)` is converted through this same rule, not silently truncated.
- **Period:** `period_start` is the first organization-local calendar date of a month; `period_end` is its last date. Work is attributed by `work_date`, including overnight shifts. The included population is every employee whose employment window intersects the period, including joiners/leavers. Freeze the population as well as each person's values, so a new hire or changed employment date cannot escape the publish drift check.
- **Published population changes:** Keep the original run and its population snapshot immutable. A newly eligible person creates a run-level drift; remediation issues that person's first, supplemental revision-0 payslip under the original period/run, with its own frozen inputs and delta posting intent. A person whose published entitlement shrinks, including complete historical ineligibility, receives a linked revision with the recomputed smaller or zero entitlement and a reversing delta. After publication, drift detection compares live eligibility with each person's **latest published slip snapshot plus any supplemental entrants**, so a resolved correction is not rediscovered merely because the original run snapshot remains immutable. Neither path creates a second live monthly run.
- **Current payslip and revision namespace:** For each org/person/month, current means the highest numbered **published** revision. Failed, cancelled and draft slips stay auditable but never enter `/mine`, current-slip/flag lookup, previous-net comparison or published revision allocation. A person-period lock and a published-only unique index protect revision 0 and each later number during publication; a draft's provisional revision number does not reserve one.
- **Publishing gate:** `BreakFacade.unresolvedBreaches` already blocks only a pending attendance/pay consequence or an unanswered `require-explanation`. `warn`, `notify-manager`, advisory, suppressed, waived, and an answered explanation do not block. Attendance blocks missing, open, not-evaluated or stale employed days, pending corrections and unresolved review items. A visible `inputs_changed` marker is a hint; the live fingerprint check is mandatory.
- **Post-publication blockers:** Opening or resolving a pending correction, attendance review item or consequential break finding emits a durable lifecycle event even when no calculation/input version changes. The published-period sweep also calls both blocker facades. A blocker-only flag may be resolved without a new payslip only when the live input fingerprint still matches the published snapshot and both blocker queries are clear; changed inputs require a revision, even when the money delta is zero.
- **No full accounting module yet (G6):** An idempotent, balanced `ledger_posting_intent` is the Step 9 posting contract behind a narrow `LedgerFacade.post`. Step 9 does not invent chart-of-account IDs. The intent stores semantic debit/credit roles and accepted account mapping/version; publishing fails if a required mapping is absent. Accounting later consumes each intent once and records the resulting journal link.
- **Sensitive access:** Employee slips are visible only after publication. `mine` is always own-only. Payroll managers can view other published slips through `payroll:view` and the P2 loader flag from `holdsPolicy(ctx, 'payroll:manage')`; any use is audited. No amount or frozen JSON is logged.

## Handoff to accounting (P6)

Accounting consumes each balanced `posting` intent once and records the journal ID; it consumes a `zero-delta-revision` marker without creating a journal. It must not recompute payroll or edit published payslips. Supplemental population-entry slips and later revisions contribute only their signed delta intent. The accepted payroll config, source evidence and immutable line bases remain the audit source for the amount that was published.
